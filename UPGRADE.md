# Обновление и перенос данных

## Переход с архива версии 1.2

Исходный архив не менялся. Версия 2.0 — отдельный пакет. Не запускайте два экземпляра с одним токеном бота или одними ключами Telegram-сессий. Перед переносом остановите **только старую службу этого проекта**, предварительно проверив её фактическое имя через `systemctl cat`.

1. Сохраните старую БД в формате `pg_dump --format=custom --no-owner`, старую конфигурацию с ключом `SESSION_ENCRYPTION_KEY`, каталог старых отчётов и старый код. Ключ не генерировать заново.
2. Проверьте дамп через `pg_restore --list`, а затем `scripts/verify_restore.py`. Сохраните исходники/копию на отдельном носителе. Не делайте перенос на единственной рабочей копии.
3. Создайте отдельный экземпляр через `scripts/install_ubuntu.sh`. **Пока не выполняйте activate**: созданная новая БД должна быть пустой для восстановления.
4. Восстановите старый дамп в новую отдельную БД от её роли. Для стандартного `tgviewer2`, если дамп доступен текущему пользователю:

   ```bash
   sudo -u postgres pg_restore --dbname=tgviewer2 --role=tgviewer2 \
     --no-owner --no-privileges --exit-on-error < old-viewer.dump
   ```

   Здесь намеренно нет `--clean`: при конфликте скрипт должен остановиться, а не удалять существующие таблицы. Адрес кластера и порт должны соответствовать выбранной установке. Если восстановление завершилось ошибкой, не запускайте миграцию; выясните причину на этой новой базе.

5. В `/etc/tgviewer2/app.env` перенесите старые `BOT_TOKEN`, `MAIN_ADMIN_ID`, `API_ID`, `API_HASH` и **тот же ключ шифрования**. Сохраните новые `DATABASE_URL` и пути отдельного экземпляра. Владельцем файла остаётся root, группа — `tgviewer2`, права — 0640. Не печатайте файл в терминал/логи.
6. Старые XLSX можно сохранить отдельно или скопировать в новый каталог отчётов с правами 0600 и владельцем `tgviewer2`. Данные отчётов версии 2 генерируются заново из БД, поэтому старый абсолютный `report_path` не используется для отправки произвольных файлов.
7. Запустите `scripts/deploy.py activate --instance tgviewer2`. Миграция добавляет поля и таблицы, сохраняет существующие номера аккаунтов, зашифрованные сессии и историю. Старые незавершённые задания отменяются с причиной `legacy_migration`: версия 1.2 не хранила полный план и безопасно восстановить его невозможно.
8. Первая миграция включает общую паузу. Проверьте владельца, количество аккаунтов, каналы, прокси и один отчёт. Выполните новый короткий тест. После проверки снимите общую паузу. Повторный запуск уже применённой миграции состояние паузы не меняет.
9. Убедившись в работоспособности, оставьте старую службу выключенной. Сохраните её код и исходную копию БД на время проверки новой версии.

Старые отчёты содержат только результаты, которые успела записать версия 1.2. Число пропущенных в прошлом аккаунтов нельзя достоверно восстановить. Полный заранее зафиксированный план доступен для новых заданий 2.0.

## Последующие обновления установленной 2.x

Распакуйте новый пакет в отдельный каталог и выполните оттуда:

```bash
sudo bash scripts/update_ubuntu.sh --instance tgviewer2
```

Скрипт сначала собирает новый релиз и окружение, пока старый бот работает. Затем останавливает только `tgviewer2.service`, создаёт проверенную по каталогу копию БД, сохраняет `before-update-<дата>.json`, применяет миграцию, запускает read-only doctor, переключает `current` и запускает службу. Проверьте её журнал и `/start`: мгновенный статус systemd ещё не доказывает успешный вход в Telegram.

Если шаг после остановки не удался, служба остаётся остановленной, старый релиз и дамп сохраняются. Другие службы не перезапускаются. Перед каждым обновлением полезно выполнить полный тест восстановления копии, особенно при новой версии схемы.

## Откат

Между совместимыми версиями схемы:

```bash
sudo python3.12 scripts/deploy.py rollback --instance tgviewer2 ИМЯ_КАТАЛОГА_РЕЛИЗА
```

Команда проверяет старый релиз через его doctor, затем переключает только код и перезапускает эту службу. Используйте её для релизов, установленных данным установщиком. Версия схемы должна поддерживаться выбранным кодом.

Для отката через несовместимую миграцию или обратно на 1.2: остановите новую службу, восстановите **предмиграционный дамп в ещё одну отдельную БД**, направьте старый код на неё, используйте сохранённый старый ключ и проверьте работу. Не подключайте старый код к изменённой базе и не удаляйте единственную копию текущей БД. Изменения, появившиеся после резервной копии, при таком откате не переносятся автоматически.

Ни установщик, ни обновление, ни откат кода автоматически не выполняют `DROP DATABASE` рабочей базы. Единственное автоматическое удаление БД есть в `verify_restore.py`, и оно относится только к случайно названной БД, которую этот же запуск создал для проверки.
